# 侦察报告：GitHub 多 agent 开发闭环的现有组件（2026-07-08，v2）

## 结论

最小闭环（builder 开 PR → reviewer 评论 → builder 修复 → 人工 merge）所需组件全部有成熟现货，属于"买"而非"造"。**v0 选型：builder = Claude Code GitHub App，reviewer = Codex GitHub App**，两者通过 GitHub 的 PR 与评论交接。地基采纳 `cobusgreyling/loop-engineering`（6587 star、MIT、活跃），其 fork 本身已 loop-ready（loop-audit 分 100、L3），故不必再跑 loop-init 脚手架。

## builder：Claude Code GitHub App

- issue 内 @claude → 读需求、建分支、实现、开 PR；PR 评论内 @claude → 向 PR 分支推修复 commit。
- 本地 `claude` 跑 `/install-github-app` 完成安装，配 ANTHROPIC_API_KEY secret。
- 是 GitHub App，靠 app 集成响应事件。

## reviewer：Codex GitHub App

- `@codex review` 在 PR 评论触发审查；或在 Codex 设置开启 Automatic reviews，PR 一开即自动审，无需 mention。
- 审 PR diff，读仓库内最近的 AGENTS.md 的 Review guidelines，贴标准 GitHub review，聚焦 P0/P1 高优风险。
- 亦有 openai/codex-action（约 10 行 YAML）供更细控制。
- 是 GitHub App。

## 关键结论：GITHUB_TOKEN 坑被规避

先前担心的"默认 GITHUB_TOKEN 创建的 PR/评论不触发下游 workflow"仅是"事件驱动的 GitHub Actions 互相触发"这种调度方式特有的坑。本架构 builder 与 reviewer 皆为 GitHub App，Codex 的 Automatic reviews 按 PR-opened 事件由 app 集成触发，与开 PR 者身份无关，因此不受该限制。此结论需在 v0.0 步骤 3 用一个由 Claude App 开出的测试 PR 实测确认。

## 地基复用清单（fork 已自带）

- 根 AGENTS.md、LOOP.md、loop-constraints.md、STATE.md、loop-run-log.md、loop-budget.md 均已存在。
- loop-constraints.md 已含：push 前先告知、禁自动 merge、最多 3 轮修复 + loop-guard 机械熔断、denylist 路径。
- npm 工具经 npx 独立获取：loop-audit（Loop Readiness 打分）、loop-cost（token 预算估算）、loop-init（脚手架，本项目不需要）。
- pr-babysitter 模式、L1-L2-L3 分级、STATE 的 Post-Run Critique（内建 retro）、multi-loop 协调文档、loop-worktree（并行隔离）。

## 造还是买

买。全部组件用现货拼装，本项目自身只产出：AGENTS.md 的 Review guidelines 段、少量约束追加、流程文档、retro 记录。不写任何 orchestrator 代码。

## 成本

单轮全链路（build + review + fix）的 token 费用分属 Anthropic 与 OpenAI 两处账单，口径不定。以首个真实 issue 实测为准，实测前不做批量调用；用 `npx @cobusgreyling/loop-cost --pattern pr-babysitter` 取参考区间。
